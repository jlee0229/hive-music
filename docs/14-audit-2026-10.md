# HiveMusic audit, October 2026

Written 2026-10-12 and checked against branch `frank/auto-sync` at commit `05d5f10`, which is also `main` of `piar1243/hive-music-official`. "Fixed" means a commit for it is on that branch; hashes are in Appendix A. **Nothing here is deployed.** The code is pushed and CI is green, but playhivemusic.com and its server still run the September build until someone deploys both (section 3, first row). The raw findings, logs, screenshots and measurements behind this report are on the machine that ran the audit, in `D:\HiveMusic-audit\`, and are not in the repository.

## 1. Summary

The agents filed 192 findings: 148 fixed, 18 partly fixed, 21 open, 5 judged not worth fixing. Twelve repeat another agent's finding. A final real-stack party simulation ran eight scenarios: the server-restart one failed and two others each exposed one bug; the restart failures were then fixed and the scenarios pass on the final code.

The five that mattered most:

1. **Anyone who knew the room code could take over the music.** The server handed the host's secret key to any caller (confirmed in production). Fixed.
2. **One guest could freeze a party or crash the server** with a single crafted message or a cheap script. Fixed.
3. **Strobe landed between the drum hits.** Three separate causes were fixed; correct tempo went from 138 of 210 test tracks to 210 of 210.
4. **A stranger's upload played at everyone's party**, with no delete, and any guest could spend paid AI calls. Fixed.
5. **Big rooms and bad Wi-Fi.** Server output at 100 phones fell from 8 723 kB/s to 190 kB/s; simulated venue-Wi-Fi runs with a clock error past 30 ms fell from 7 in 40 to none.

The largest open item is yours: production runs on 256 MB, and one long upload needs more.

## 2. What was fixed

### Security and abuse

- **Host takeover.** The server gave the host key to anyone who asked with the room code, and a guest could also claim host by reusing the host's public ID. Now only the key grants host rights. (SG-01, SG-02, HOST-04, HOST-16)
- **Freezing a room.** One guest message (an ID such as `toString`, or the number `1e999`) made every later update unreadable on every phone. Such messages are refused. (PROTO-01, PROTO-02, SG-05)
- **Crashing the server.** A guest could force "4.00 MB per broadcast", one socket could add 5,000 fake phones, and 20,000 rooms could be created and never cleaned up. Messages are capped at 64 KB (was 16 MB), rooms at 256 devices, the server at 2,000 rooms. (PROTO-03, SG-04, SG-05, SG-06)
- **Vibe button open to guests.** Anyone with the code could rewrite the mode timeline and spend paid AI calls (19 accepted before a limit applied). It now requires the host key. (SG-09, RT-01)
- **Limits and privacy.** Rate limits could be dodged with a forged header; codes could be guessed over 100 times a second (now 60 a minute); every guest received everyone's name and phone model (now only their own). (RT-04, SG-14, RT-05)
- **Proof.** With a new hostile-input fuzz test, the suite caught 19 of 19 deliberately re-introduced bugs, and a later red-team pass could not take host or poison a room. (SG-13)

### Sync and audio

- **Venue Wi-Fi.** Simulated worst first lock 4.31 s → 1.35 s; steady error (p95 / max) 7.3 / 137.9 ms → 2.4 / 5.1 ms; runs past 30 ms 7/40 → 0/40. Recovery after a clock step, as after sleep: 10.3 s → 16 ms. (ENGINE-SYNC-05, -22, SCALE-NET-06)
- **Calls, Siri, lock screen.** A phone could return as overlapping copies of the song, or hang on "Resuming…". In a real browser a 6-second pause built 24 sound sources before, 0 after. (ENGINE-SYNC-03, -12, -16, -17, -18)
- **Removed phones kept playing** (RMS 0.51 after 4.5 s); now silent. (ENGINE-SYNC-10, PLAYER-UI-01, -20)
- **A failed download meant silence for the whole song.** Phones now retry, and the server repeats room state every 5 s while playing. (ENGINE-SYNC-02, -23, -P5)
- **Song edges.** Every song lost its last 600 ms; a joining phone stop-started after about 2 s. (ENGINE-SYNC-09, -04)
- **Next song late, and a gap between songs.** Phones now download the next song ahead of time: in the real-stack run every phone had it 19–26 s before its start, and its first sound landed within −16 to +10 ms of schedule. That did not shorten the pause. The server still waited 5 s before starting the next song, so guests heard 4.9–5.0 s of silence at every song change (4946–5005 ms before the pre-download, 4939–4993 ms after). The wait is now 2 s, re-measured on the real stack at 1.95–2.0 s with every phone starting the new song within 10 ms of schedule. A change with no gap needs phones to report that the next song is ready, which is open. (ENGINE-SYNC-21, SCALE-NET-05 in part, PARTY-03 in part)
- **Tuning moment.** One bad microphone sample no longer blinds later clicks; echoes veto fewer clicks (misses 27.5% → 21.9%); dropped microphone frames no longer produce false offsets; the server ignores implausible results. (ENGINE-DSP-40, -41, -44, -45)
- **Smaller engine faults**, several found by a new randomized test; a three-simulated-hour soak ends at 0.58 ms worst error. (ENGINE-SYNC-07, -08, -11, -13, -14)

### Modes and tempo

- **Strobe off the beat, three causes.** Tempo detection: acceptable on 138/210 test tracks → 210/210; strobe within 30 ms of the beat 35/210 → 209/210. Rounding: at 128 BPM the switch was 128 ms late by 4:00; now exact. Stale patterns after a setting change: 72 of 300 writes refused in a real browser → 0 of 294. (ENGINE-DSP-01, -02, -03, PROTO-08, ENGINE-SYNC-06)
- **Strobe dead air.** Two phones on two groups could be silent 51 % of the time, and the room dropped out for an instant at every hand-off. (PROTO-07, -09, HOST-17)
- **Orchestra, Stereo, Wave.** Orchestra dropped instruments with few phones; Stereo played half a song with one side empty; Wave did nothing unless phones had been dragged on the map. (PROTO-04, -05, -06)
- **Choir.** Turned on mid-song it never played; voices were up to 43 ms early (now within 5.3 ms on music); a lone phone could sing with no root. Peak memory after a second voice change: 176 MB → 89 MB. (ENGINE-SYNC-01, -15, -19, -20, ENGINE-DSP-20 to -23, -26, PROTO-10)
- **Older tabs froze when Choir was on**, and a vibe plan carried over to the next song. (PROTO-13, -14, SG-10)

### Host screen

- **After a restart** the host page hung on a spinner or a dead stage; it now gets its room back or shows a way out. (HOST-03, -05, SG-01)
- **Start and tuning.** A double tap restarted the song; the stage claimed tuning had happened when it had not; Cancel was off-screen from 9 phones up. (HOST-07, -08, -15, DESIGN-01)
- **Map.** Phones after the 19th stacked on one dot (231 overlapping pairs at 40 phones → 0); taps read as drags; the map swallowed scrolling. (HOST-02, -14, -18, -21, DESIGN-02)
- **Controls.** Tapping the current song stopped the music; the host could remove themself; the host's own speaker silently switched off after a reconnect; errors showed developer text and never cleared; Strobe and Choir chips were off-screen on small phones. (HOST-06, -09 to -13, ENGINE-SYNC-P1, -P3, DESIGN-08)

### Guest phones

- **Joining.** A phone whose audio would not unlock never joined; every join flashed "Tap to resume"; a loading phone looked like a broken one. (PLAYER-UI-02, -03, -04)
- **Strobe on the screen.** 4.4 full-screen flashes a second at a brightness swing of 0.42, above the photosensitivity guideline; the swing is now capped at 0.090 (limit 0.10). Dark-phase text contrast 1.27:1 → above 4:1. (PLAYER-UI-05, -06, DESIGN-03, -04)
- **Codes and identity.** Wrong codes are reported on arrival; the join link in the host's browser no longer hijacks the host; the projector page is no longer a phantom speaker; after a restart, guests who return before the host are held up to 15 s instead of stranded. (PLAYER-UI-09 to -15, -24, SG-03, SG-15)
- **Fit.** Screen captures with clipped content: 53 → 19. "Tap to join" is on screen on small iPhones and contrast passes. (PLAYER-UI-07, -08, -16 to -19, -26, -30, DESIGN-06, -07, -09)

### Scale (many phones)

- **Full guest list sent to everyone.** Server output at 100 phones 8 723 → 190 kB/s; at 200, 34 581 → 350 kB/s. (SCALE-NET-02, -10)
- **Frozen phones.** Ten stalled phones added 142 MB of server memory; now 10 MB. (SCALE-NET-03)
- **One upload stalled every party.** A bystander's worst clock round trip: 102 ms → 2 ms. (SCALE-NET-04 in part)
- **Also:** a real load-test tool, staggered reconnects, a tuning timeout that grows with the room. (SCALE-NET-01, -09 in part, ENGINE-SYNC-P4)

### Uploads and library

- **Strangers' songs at your party.** Every upload appeared in every hive's list and rotation, with no delete. Uploads now belong to the uploading browser; owners can remove them; 40 tracks and 400 MB each. (RT-02)
- **Hostile files.** A 1.2 KB file became 53 MB on disk; a 44-byte file made a track that broke rooms. A 4-minute upload peaked at 201 MB, then 157 MB (178 MB in a later re-measurement). (SG-07 in part)
- **Also:** one corrupt file no longer hides the library; partial audio requests return the right bytes; over-long files are refused before decoding. (SG-08, SG-12, HOST-12)

### Deploy, CI and docs

- **Deploys and CI.** The deploy workflow failed on every push; it is now manual. CI runs lint, build, browser tests and an image smoke test. (INFRA-01, -02)
- **Server.** Image pinned, 10 packages instead of about 450, non-root; clean shutdown; `/health` counts rooms and phones; an operator log. (INFRA-03, -04 in part, -05 in part, -16)
- **Docs and mock.** Docs describe the product, and the mock server's 17 differences from the real one are now 5. (INFRA-06, -07, -08, -15, PROTO-11, -12, -15, -16, -17, HOST-01, -19 in part, PLAYER-UI-25)
- **Tests.** Before: 258 unit tests, 36 of 40 browser tests passing. On the final tree (`05d5f10`): 784 unit tests, all passing (protocol 140, server 214, sync-client 338, web 92), and the browser suite at 192 passed, 4 skipped because they need a real server and real audio; the one failure in that run was a timing race in a test, fixed in the next commit. GitHub CI on Linux is green on all three jobs for `05d5f10`: typecheck, lint, unit tests and web build; the browser suite; and a real build and smoke test of the server image. On the real stack, the basic party, playlist, guest-behaviour and both restart scenarios pass.

### Bugs the test double was hiding

The browser tests run against a stand-in ("mock") server. It sent every guest the whole room, while the real server now sends each guest only their own record. Tests therefore passed on things that could not work at a real party. Two were found:

- **"Waiting for the host to come back" never appeared.** The guest page looked the host up in a guest list it no longer receives. The server now tells guests directly whether a host is connected. The real-stack party run found the same bug independently. (PLAYER-UI-18, PARTY-07; commits 9b387e2, 25844bb)
- **The guest's tuning bar never moved.** It sat on "Phone 1 of 12" for the whole tuning moment, because it counted other phones' results, which a guest is never sent. It now follows the tuning schedule. (MOCK-PARITY-01)

The mock now sends each guest exactly what the real server sends; a probe run against both differs in two lines, both deliberate. The full browser suite passed against it before any app change (178 passed, 4 skipped). One flaky contrast test turned out to be a real one-frame glitch, the previous part's text colour on the new part's background, and is fixed. (MOCK-PARITY-02, HOST-19)

Findings from the run:

- **PARTY-01 (P1). A server restart while the host's tab is away ejects every guest for good.** Guests reconnect, wait 15 s for the host, then get "Hive not found" with their audio shut down. The host returned 33 s after the restart to the same code and 0 players; 40 s later the guests were still on "Hive not found". This is ENGINE-SYNC-P2 seen for real. **Fixed** (d8aa63c, ddfef41): the server now holds a returning guest for the whole two-minute restart window instead of 15 s, and a guest who had already joined waits on "Waiting for the host to come back", silent, asking again every 30 s, for five minutes before giving up. On the final code the real-stack run let all three guests back in when the host returned 30 s after the restart, and they were sounding 7.9 s after that. A mistyped code still says "Hive not found" at once. Not exercised on the real stack: a host away for more than two minutes.
- **PARTY-02 (P1). A restart with the host present stops the music until the host presses Start.** Everyone reconnects by themselves in 4.9–6.0 s, but the room comes back stopped, on the first song in the library rather than the one that was playing, and Start runs the tuning moment again: music at 13.0 s at best, never if the host is not watching. This is the measured form of SCALE-NET-08 and INFRA-05. **Fixed** (29439de, a9d0b38): the host page remembers the show and, when the server has re-created the room, puts back the song, the mode and the position by itself, without a tuning moment. On the final code the real-stack run measured 0 ms of silence for guests across a restart: they keep playing what was already scheduled, reconnect in 5.0–5.7 s, and the timeline is restored within 1 ms of the old one. A show that was paused or stopped comes back paused or stopped. It needs the host page open; tuning offsets, a vibe plan, dragged map positions and pinned parts are not restored.
- **PARTY-03 (P2). About five seconds of silence between every two songs.** Reduced to 2 s (commit bb34dc7); re-measured on the real stack at 1.95–2.0 s. A change with no gap at all is open.
- **PARTY-04 (P3). Every iPhone guest's join page logs a rendering error on load**, because the silent-mode banner is decided differently on the server and on the phone. No visible effect was reported. **Fixed** (ddfef41): the device and the remembered name are read after the page has loaded; the real-stack basic party now runs with no page errors in any browser.
- **PARTY-05 (P3). In Wave, two of five untouched phones get the same delay** (97 ms each), because the automatic layout puts one above the other. Left as it is, by design: Wave sweeps across the map, so two phones at the same place along the sweep are meant to sound together. Drag one and its delay follows.
- **PARTY-06 (P3, low confidence). After an automatic song change the phones start further apart** (12.4 ms, settling over about 18 s) than after Start. Seen in one scenario and not in another; may be the test computer under load. Open; needs real phones.
- **PARTY-07 (P2). Guests are never told the host has gone.** Fixed (9b387e2, 25844bb); the same bug as the first item under "Bugs the test double was hiding". The findings file still says proposed.
- **PARTY-08 (P3). Polish seen in the screenshots.** Partly fixed. The host's legend no longer lists drums, bass, vocals and other in Unison, Wave and Strobe (checked in code; host design pass). A paused guest's card now reads "Song ready" instead of "Downloading the song", but it is still shown. No commit was found that changes the instrument colours Strobe groups are painted in. Whether a name still touches the neighbouring dot at five phones was not checked.

## 4. Decisions only the founder can make

1. **Server memory.** Production has 256 MB plus 512 MB of swap; the coordinator kept that so a deploy cannot change the bill. Options: stay; 512 MB (one upload at a time fits, four do not); 1 GB. server-guard and infra-docs recommended 1 GB, red-team 512 MB or 1 GB, scale-net a dedicated core for a paid tier. (INFRA-04, RT-03, SG-07, SCALE-NET-15)
2. **Licence.** With none, the public code is all rights reserved. Options: leave it, MIT/Apache, source-available, or a private repo. infra-docs recommended nothing, noting it is a joint decision with the co-author. (INFRA-09)
3. **Terms, privacy, takedown.** The site serves uploaded music with none of these. infra-docs proposed a terms page, a privacy note and a monitored abuse address, or making uploads private to a room and deleted when it ends. (INFRA-10)
4. **Songs already in production.** They have no owner, so they stay shared with every hive and cannot be removed through the app. Options: keep them as the shared library, remove some by hand (runbook section 6), or set `LIBRARY_SCOPE=global` for the old behaviour. red-team and server-guard had proposed sharing only curated tracks. (RT-02, SG-07)
5. **Co-hosting.** Sharing the host link no longer makes a second host. Options: one host only (now), or a deliberate co-host link carrying the key (server-guard's suggestion). (SG-16)
6. **Strobe on screens.** design-critic recommended capping the screen at 3 flashes a second; player-ui kept the rate and capped brightness, so fast strobe becomes a shimmer. Judge it on a real phone. (DESIGN-03, PLAYER-UI-05)
7. **Wave span.** An untouched room of 2–6 phones sweeps 38 % of the span. Stretching it over whoever is present means a new arrival re-times everyone. protocol-planner left it as is. (PROTO-04)
8. **Room limits.** Codes have 4 characters (923,521 possibilities); server-guard recommends 5–6 or a token in the QR. Rooms cap at 256; the declared limit of 64 is not enforced. (SG-14, SG-04, SCALE-NET-13)
9. **Sound taste.** Slow songs report their true tempo, so "1 beat" is slower on them. Should drums stay unpitched in Choir? Is the octave-down voice audible, and is "tenor" the right name for the fifth above? (ENGINE-DSP-05, -25, PROTO-10)
10. **Tuning** runs once per room; later arrivals are tuned only if the host taps "Tune the hive". It also plays one click per phone, so Start takes 16.4 s at 30 phones and 28.9 s at 60: cap it, or skip it automatically in big rooms? (HOST-07, SCALE-NET-09, party simulation)
11. **Design questions still open:** the "+60 ms" figure on the host's Players rows, the per-phone nudge slider and the HOST badge (all kept by the design pass, listed in section 2); Unison as a white screen; where the vibe box belongs; confirm before switching song mid-song; "phones" or "players"; "YOU ARE OTHER"; whether a tap on empty space with the keyboard open should join. (HOST-09, HOST-20, design review)
12. **Smaller calls** are in the findings named here: PLAYER-UI-01, ENGINE-SYNC-P1, ENGINE-DSP-45, SCALE-NET-05, INFRA-02, INFRA-10, INFRA-14, INFRA-15, SG-16.

## 5. What could not be tested here

No physical phone, speaker or venue network was used; phone speed and audibility figures are estimates. The party simulation ran the real software, but every "phone" shared one computer, one clock and a fake microphone. So it could not observe four things: whether real speakers are in time with each other in the air; what a real lock screen or phone call does; how long Choir takes to render on a phone (0.47 s on the test desktop); and whether the tuning moment helps (the fake microphone hears nothing useful, so the run only showed that tuning does no harm). Fly and Vercel were never exercised by this audit, and the manual deploy workflow has never run. The CI workflow, image build included, has run on GitHub.

**Fifteen minutes, three phones** (an iPhone as host, an Android, one more):

1. **Join (2 min).** Scan the QR. Is "Tap to join" visible without scrolling? Does the iPhone play with its silent switch on?
2. **Start (2 min).** Allow the microphone. One click per phone, then music? Does each guest's tuning bar advance? In Unison at arm's length, is there an echo, and is it smaller than when you tap "Skip tuning"? Does the Android stutter about 2 s after joining?
3. **Strobe (2 min).** At 1/4 and 1/16 with 2 groups: does the switch land on the drum hit, at the start and after 3 minutes? Change the division mid-song: do all phones follow together? Is the screen shimmer acceptable?
4. **Choir (2 min).** Turn it on mid-song. Time how long each phone takes to change pitch. Does it stay in time? Does the iPhone tab survive?
5. **Interruptions (2 min).** Lock the iPhone for 20 s; trigger Siri; call one phone. Does one tap on "Tap to resume" bring it back in time, with no burst of sound?
6. **Song change (1 min).** Does the last note play out? How long is the silence (about 2 s expected)? Does the next song start together on all three, and stay together for the first 20 s?
7. **Remove (1 min).** Remove a phone on the map. Is it silent at once?
8. **Map (1 min).** On both phone types: a swipe on the map scrolls the page; dragging a dot moves the dot.
9. **Upload (1 min).** Upload from the host phone while it plays. Does playback survive? Remove the song.
10. **Networks (1 min).** Put one phone on cellular, then on a Bluetooth speaker. Is it steadily early or late?

Also needing a person: one walk through the runbook (deploy, verify, roll back) before it is relied on.

## Appendix B: where the sources disagree

- **Strobe on screens.** design-critic says the cap is undecided and proposes limiting the rate; player-ui says fixed, by limiting brightness instead. Both are accurate. The code has player-ui's version; the choice is in section 4.
- **Health data for projector pages.** The design pass write-up says the real server still does not send it. server-guard says fixed (56c19db). The code agrees with server-guard.
- **Five failing engine tests.** server-guard, host-ui and design-critic each report 5 failures in the engine package; engine-sync reports none after its fix (cd54fea). Those three branches predate the fix. The coordinator's run of the merged tree settles it: 337 passing, 0 failing.
- **Machine memory.** infra-docs set 1 GB; the coordinator set it back to 256 MB, and `fly.toml` records that as what production actually runs. server-guard and scale-net called the size unverified; the `fly.toml` note is later and specific, so I use it.
- **Memory for a 10-minute upload.** `fly.toml`, `CLAUDE.md` and, since commit 9c9897f, the runbook all give the post-fix figures (about 280 MB; the runbook says 271 MB, server-guard's second measurement). The earlier 363 MB was measured before the fixes.
- **Party-simulation statuses.** The findings file marks all eight PARTY findings "proposed" or "needs-human". PARTY-07 is fixed and PARTY-03 is reduced by commits made after the file was written; the code agrees with the commits.
- **Late-join time.** The party findings file says 220 ms; the raw result (`05-guests.json`) says 218 ms. The report quotes the file.
- **MOCK-PARITY-02.** The findings file says "proposed". The coordinator's commit 25844bb applies the fix the file recommends, and the code shows it, so the report says fixed.
- **Design write-ups against later work.** The host design write-up counts 10 font sizes before; its own commit message says 9, and the write-up calls that a miscount. The guest write-up reports 133 protocol tests; the merged tree has 139 because the mock-parity work added tests afterwards.
- **Calibration bounds.** engine-dsp proposed ignoring results beyond 100 ms; the server uses 200 ms plus an offset range. scale-net proposed 50 ms of timeout per phone; the server uses 100 ms.
- **"Waiting for the host to come back".** player-ui reports this fixed (PLAYER-UI-18), and server-guard reports that nothing on the guest side reads the guest list. Both cannot hold: once guests stopped receiving the guest list (SCALE-NET-02) the line could never appear against the real server. The coordinator's commit 9b387e2 says so and repairs it, and the mock-parity file confirms the cause; I believe those.
- **Map capacity.** design-critic says phones stack "after the 18th", host-ui and protocol-planner say after the 19th. The planner's arithmetic (1 + 6 + 12 slots) supports 19.
