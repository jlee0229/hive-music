The FIRST estimate was 4.889 ms off and that is not a bug: one probe cannot separate path asymmetry
(offset = trueOffset + (d1 - d2)/2) from the offset itself. Nothing in the design protects it - the
first estimate is adopted directly because slewing from nothing is meaningless. What fixes it is the
window filling: the 20-pair burst over NTP_BURST_WINDOW_MS = 4000 runs at connect, long before a host
presses Play. Consequence for the demo: a phone that joins and is played to within ~1 s of connecting
can be several ms out. The Lobby's "waiting for phones" step already covers this; it is worth not
shortening.

--- NEGATIVE RESULT: coded probe pairs add nothing measurable on top of min-RTT ---
The brief asks for coded probe pairs, and they are implemented and exercised end to end (the server
echoes probeGroupId/probeGroupIndex; `createHiveClient` only ever produces an offset if a pair
validated). But I could not construct a traffic model in which they improve the estimate:

  scenario                                    worst settled error, pairs ON / OFF
  +-30 ms path jitter, 20 % spikes of +80 ms        1.942 ms / 1.942 ms
  small one-directional queueing (+4 ms, 25 %)      1.633 ms / 1.577 ms  (20 seeds)
  first pair deliberately queued +80 ms one way     0.000 ms / 0.000 ms

The reason is structural: a queueing spike that skews the offset by d/2 also raises that probe's RTT
by d, so min-RTT selection outranks it on the very next clean probe. Coded pairs can only beat
min-RTT on delay that is asymmetric *without* costing RTT, which no simple model produces and which
real networks produce rarely (it needs the up and down paths to change in opposite directions inside
10 ms).

Kept anyway, deliberately: the fields are already in the frozen protocol, the cost is one extra probe
per second, and the failure mode it guards against is the one that would be invisible in testing and
fatal on stage. The test that records this is named "(negative result)" so nobody later mistakes it
for a win. If the clock budget ever needs to be cut, this is the first mechanism to drop, not
min-RTT.

A safety valve was needed, though, and is implemented: if strict pair validation accepts nothing
within the first NTP_BURST_WINDOW_MS, the model relaxes to the better half of a pair and sets
`clock.degraded = true`. A phone with no clock cannot play at all, so a degraded clock beats none.
/diag can surface the flag.
